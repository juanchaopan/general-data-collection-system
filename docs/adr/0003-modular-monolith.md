# ADR-0003 架构风格：模块化单体，同代码的后台任务模式

- 状态：已接受
- 日期：2026-10-30
- 相关需求：REQ-018、019、021、022、027；架构指标（见 `docs/architecture/overview.md`）

## 背景

规模：几千机构、几万用户，峰值 1000 到 3000 并发，一个模板一轮约 1500 万个单元格值。强一致要求：单元格保存与其审计、提交与快照必须同一事务。维护：AI 开发和维护，用户做产品负责人，运维越少越好。早期原型的教训之一是"一个项目 6.4 万行、分层混乱"。

## 候选方案

| 方案 | 优点 | 缺点 | 适合条件 |
|---|---|---|---|
| 模块化单体 + 同代码后台任务模式 | 事务简单；审计与数据同事务；运维最少；公式引擎与浏览器复用同一份 TypeScript；边界清楚，以后可拆 | 模块边界靠工具和纪律守住 | 规模中等、维护人少、强一致要求高 |
| 微服务 | 独立扩容和发布 | 跨服务事务难，审计难与数据同事务；部署和排错成倍复杂；没有指标要求独立扩容 | 团队大、模块需要独立发布 |
| 不分模块的单体 | 最快起步 | 早期原型就是这样走坏的 | 一次性小工具 |

## 决策

采用模块化单体。同一份后端代码用环境变量 `ROLE=api|worker` 选择运行模式：API 模式处理请求，worker 模式只消费队列和定时任务。两种模式共享领域代码和数据库。

不为"分布式"而分布式。每多一个独立部署的服务，就多一份部署、监控、升级和排错；现有指标没有任何一项要求这样做。

## 证据

无探针。依据是架构指标与 ADR-0001 的结论（公式引擎是 TypeScript，浏览器和服务端可复用同一份）。

## 后果

- 好处：事务和审计简单；运维少；部署一个镜像；本地一条命令起全套。
- 代价：模块边界要靠 dependency-cruiser 强制（ADR-0004）；一个模块的缺陷可能拖垮进程，所以要有健康检查和多实例；发布按整体进行。
- 什么时候应该重新考虑：后台任务严重影响 API 响应；某个模块需要独立扩容或用不同技术栈；团队扩大到需要独立发布的程度。
