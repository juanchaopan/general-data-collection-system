# ADR-0006 身份认证：Keycloak，授权由应用自己做

- 状态：已接受
- 日期：2026-10-30
- 相关需求：REQ-002、003、004、014、031；ADR-0002；Q-001

## 背景

网页端和 Excel 加载项都要登录（ADR-0002 已定：对话框 + 授权码 + PKCE）。上线后的身份提供者未定（Q-001）。登录里的密码、锁定、重置、多因素最容易写出漏洞，早期原型的权限混乱也是教训之一。

## 候选方案

| 方案 | 优点 | 缺点 | 适合条件 |
|---|---|---|---|
| Keycloak | Apache-2.0；密码策略、防暴力破解、找回密码、多因素、英法双语现成；以后可联合 Entra ID，Q-001 变成配置 | 多一个 Java 服务（约 500MB 内存）；登录主题要定制并做无障碍验证；要有备份和高可用 | 身份方案未定、安全敏感、维护人少 |
| 嵌入式 OIDC 库（node-oidc-provider）+ 自己写登录 | MIT；少一个服务 | 密码哈希、锁定、找回、多因素都要自己写、自己维护 | 有专人做安全 |
| 探针里手写的那套 | 最简单 | 无密码策略、无加密存储、无撤销与审计 | 仅验证用，不能上线 |

## 决策

采用 Keycloak（单个 realm）。

- 客户端：`web`（公开客户端，授权码 + PKCE）、`addin`（公开客户端，授权码 + PKCE，重定向到 `/addin/callback`）。API 是资源服务器，用公钥（JWKS，缓存）校验 JWT。
- **授权不放在 Keycloak**：Keycloak 只回答"你是谁"，令牌里不带角色。角色、权限和授权记录由应用的 `iam` 模块管理，因为授权范围是 (用户, 角色, 实例[, 机构])，Keycloak 的 realm 角色表达不了。
- 用户创建：应用先建"待激活"用户，再调 Keycloak 管理接口创建账号并触发设置密码邮件，成功后激活；失败由任务重试（避免一半成功）。
- 访问令牌短期（分钟级）；刷新令牌每次使用轮换；加载项令牌只放内存（ADR-0002 已验证）。
- 同一个域名：代理把 `/auth/` 转发给 Keycloak，`/addin/` 提供加载项静态文件，满足对话框首页同域的要求。
- 登录页主题：英法双语，满足 WCAG 2.1 AA，需要验证（纳入 Playwright 的 axe 检查）。
- 以后接 Entra ID：用 Keycloak 的身份代理，应用和加载项不用改。

## 证据

探针代码用完即弃，未保留在本仓库（2026-10-30，Keycloak 26.8.1，本机 JDK 21，开发模式）。完整记录见 `assets/spike-keycloak-SPIKE.md`，原始结果见 `assets/spike-keycloak-results-*.json`，登录页截图见 `assets/spike-keycloak-login-en.png`、`assets/spike-keycloak-login-fr.png`。判据 K1 到 K5 经用户确认。

| 判据 | 结果 |
|---|---|
| K1 Excel 内登录 | 通过：真人在 Keycloak 登录页输入账号密码；对话框 → 授权码 + PKCE → 调用 API 返回 200；全程同一个域名（`/auth/` 经代理）；重定向白名单外被拒；`plain` 和无 PKCE 被拒 |
| K2 续期与轮换 | 通过：令牌过期后无需密码续期；刷新令牌轮换，旧的立即作废；工作簿 A1 内容不丢；存储中未发现令牌 |
| K3 登录页 | 通过（有保留）：英法两种语言 axe 严重和重要违规均为 0；第 5 次输错锁定，锁定后页面不暴露账号已锁定 |
| K4 管理接口创建用户 | 通过：邮件随用户语言；重复和并发创建幂等；同邮箱第二个账号被拒；Keycloak 不可达时干净失败，重试成功；批量创建约 430 个/秒 |
| K5 资源与停机 | 通过：内存约 380 到 480 MB；首次启动 36.7 秒，重启 10.3 秒；停机时已签发的令牌仍可校验；重启后会话保留 |

**没有验证的**：键盘登录（用户未回答）、读屏软件、颜色对比度（axe 判断不了）、Mac 和网页版 Excel、生产模式与外部 PostgreSQL、真实 Caddy 代理、高可用、联合 Entra、邮件里的"设置密码"链接是否可用。这些记入 Q-021、Q-029。

## 后果

- 好处：不自己写密码和多因素；Q-001 不必先定；符合行业标准；对安全评估友好。
- 代价：多一个有状态服务要备份、升级、做高可用；Keycloak 管理接口的调用要处理部分失败；主题定制工作量；Keycloak 版本升级要跟进。
- **探针中发现、必须落实的设计要点**：
  1. **API 冷启动要预取公钥并重试**（或把公钥持久化）。停机时能校验令牌，是因为 API 进程里已缓存公钥；API 恰在 Keycloak 宕机时重启，会验不了任何令牌。
  2. **刷新令牌必须单飞**：客户端同一时刻只发一次刷新。Keycloak 发现已用过的刷新令牌被重放，会撤销整条链；网页端多个标签页或加载项并发刷新会把用户登出。
  3. **访问令牌去掉不必要的个人信息**：默认令牌带邮箱和姓名，隐私评估角度应通过客户端范围去掉（Q-014）。
  4. **同域代理的 Keycloak 配置**：`--hostname=https://<域名>/auth`、`--http-relative-path=/auth`、`--proxy-headers=xforwarded`；客户端设置 `pkce.code.challenge.method=S256`；刷新令牌轮换（撤销已用的）且最大复用 0。
  5. **锁定**：5 次输错锁定，另有"快速重试"保护（失败间隔小于 1 秒会提前锁 60 秒）；页面不暴露锁定。
  6. **运行方式**：本机没有 Docker 时，Keycloak 解压版加 JDK 21 可运行（见 Q-028），可作为不用容器的备选。
- 什么时候应该重新考虑：Keycloak 的运维成本超出预期；平台决定只用 Entra ID 且设计人都是 Microsoft 365 工作账号（那时可直接用 Entra）；无法满足登录页的无障碍要求。
