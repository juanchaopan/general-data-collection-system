# ADR-0004 模块边界规则（修改规范库默认的分层规则）

- 状态：已接受
- 日期：2026-10-30
- 相关需求：REQ-003、018、019、022；ADR-0003

## 背景

规范库 `node-ts` 的默认规则是"功能之间不互相引用，共用的放 `shared`"。但本项目的模块有天然依赖：填报要读模板的结构，模板要读科目表，所有写入都要记审计。按默认规则这些都要塞进 `shared`，`shared` 会膨胀成第二个"大泥球"；或者全改成异步事件，让提交、保存这类必须同步的场景变得别扭。

## 候选方案

| 方案 | 优点 | 缺点 | 适合条件 |
|---|---|---|---|
| A. 模块只能通过对方的公开入口调用，方向无环，禁止直接读写对方的表 | 贴合业务；边界清楚；以后拆服务时公开入口就是接缝 | 要改架构检查规则；要维护一张允许依赖图 | 模块化单体 |
| B. 严格禁止模块互相引用，只走事件和队列 | 与规范库默认一致，耦合最低 | 同步场景别扭；调试困难；一致性难 | 模块真的相互独立 |
| C. 随便引用 | 最快 | 回到早期原型的状态 | 不适用 |

## 决策

采用 A。

规则（由 dependency-cruiser 强制，写在 `apps/api/.dependency-cruiser.cjs`）：

1. 层内方向不变：`routes → services → repositories → domain`；domain 不依赖其他层、Web 框架、数据库驱动。
2. 模块 A 要用模块 B，只能 `import` B 的 `index.ts`（公开入口）。不允许引用 B 的 `routes`、`services`、`repositories`、`domain` 里的文件。
3. 允许的模块依赖图见 `docs/architecture/overview.md` 的"后端模块和允许的依赖"表；不在表里的依赖一律报错；不允许循环。
4. 每张表只有一个主人模块；只有主人模块的 `repositories` 可以读写它。其他模块要数据，调用主人的公开入口。
5. `audit` 不依赖任何业务模块；其他模块在自己的事务里调用 `audit` 的公开入口写审计。
6. `notifications` 不被其他模块直接调用，其他模块入队任务，`notifications` 消费。
7. `shared` 不依赖任何模块；不放业务规则，只放配置、错误类型、事务与租户上下文、批量导入框架、文件存储接口、任务封装。
8. 服务（services）不依赖 Web 框架，只允许引用类型。

## 证据

无探针。

## 后果

- 好处：边界可检查；业务同步调用自然；以后拆服务时公开入口就是接缝。
- 代价：规范库的 `.dependency-cruiser.cjs` 要改（/scaffold 时按本 ADR 配置）；新增一个模块依赖要先改依赖图并经评审；公开入口要保持小而稳定。
- 什么时候应该重新考虑：依赖图出现环的诱惑变多（说明模块切分不对）；公开入口膨胀成"什么都暴露"。
