# 需求

编号规则：REQ 加三位数字，编号不复用。作废的需求保留原文，状态改为"已废弃"，写明被哪一条替代。

状态：有效（要做）、已实现（代码里已经有，从现有系统继承）、已废弃。本项目从零重建，没有"已实现"条目。
来源：用户回答 / AI 建议，待用户确认 / 文档出处 / 代码推断（未确认的推断要请用户确认后再改成"代码推断，用户已确认"）。

"老系统"指 `GDCT_PlanB` 和 `GDCT_TDT`，路径见 `legacy-scope.md`。它们只作为"想达成什么"的证据。

## 第一期 1a：地基与模板

## REQ-001 实例管理

- 优先级：MVP（1a）
- 状态：有效
- 来源：用户回答（实例即不同项目各用一套，互相隔离）
- 用户故事：作为平台管理员，我想要创建、编辑和停用实例，以便让不同的采集项目各自独立运转。
- 验收标准：
  1. Given 平台管理员已登录，When 创建实例并指定名称和一位实例管理员，Then 实例出现在实例列表，并且该管理员获得此实例的"实例管理员"授权。
  2. Given 实例 A 和实例 B 各有数据，When 实例 A 的用户请求实例 B 的任何数据，Then 系统拒绝并记入审计日志。
  3. Given 一个实例已有已发布的模板或填报，When 平台管理员停用它，Then 实例不再接受登录和填报，数据保留，可以重新启用。
- 业务规则：
  - 实例是租户边界：科目表、机构、模板、填报、授权、审计都属于且仅属于一个实例。
  - 实例有名称（多语言，见 REQ-029）、状态（启用、停用）。
  - 实例有已被引用的数据时不能物理删除；全空的实例可以删除。
- 边界和异常：
  - 停用实例时有用户在线：当前会话在下一次请求时被拒绝，已保存的草稿不丢。
  - 重名：实例名在平台内唯一。
- 相关：REQ-003、REQ-012、Q-005；老系统：`Instance.razor`、`InstanceService.cs`、`UserInstanceRoleService.cs`

## REQ-002 认证

- 优先级：MVP（1a）
- 状态：有效
- 来源：用户回答（登录方式不确定，第一期只在本地运行）；AI 建议，待用户确认（可插拔身份提供者）
- 用户故事：作为用户，我想要安全登录，以便系统知道我是谁。
- 验收标准：
  1. Given 本地环境，When 用户用本地账号登录，Then 获得会话并只能访问被授权的内容。
  2. Given 身份提供者是可插拔的，When 以后接入 Entra ID 或其他提供者，Then 不需要修改授权和业务代码，只增加一个提供者实现。
  3. Given 连续登录失败，When 超过阈值，Then 账号被暂时锁定并提示，且记入审计日志。
  4. Given 用户被停用，When 他再次访问，Then 会话立即失效。
- 业务规则：
  - 授权（REQ-003）与认证分开：认证只回答"你是谁"。
  - 本地账号密码用强哈希保存，不可逆；不在日志中出现。
  - Excel 加载项也走同一套认证（见 REQ-014）。
- 边界和异常：
  - 会话超时：按配置时间失效，未保存的编辑见 REQ-023。
  - 未登录的人只能看到登录页和公开的帮助页。
- 相关：Q-001、Q-002、Q-011、REQ-031

## REQ-003 基于角色的授权（RBAC）

- 优先级：MVP（1a）
- 状态：有效
- 来源：用户回答（权限↔角色多对多；授权为 (用户, 角色, 实例) 三元组，实例为空表示平台级）；AI 建议，待用户确认（授权范围再细到机构，见 Q-005）
- 用户故事：作为实例管理员，我想要给用户在本实例里指派角色，以便控制谁能做什么。
- 验收标准：
  1. Given 同一用户，When 在实例 A 被授予"模板设计人"、在实例 B 被授予"填报人"，Then 他在 A 里能设计模板、在 B 里只能填报，互不影响。
  2. Given 角色由权限集合定义，When 给角色增加或移除一个权限，Then 持有该角色的所有授权立即生效，无需逐个用户修改。
  3. Given 授权实例为空（平台级角色），When 平台管理员访问任意实例，Then 只能执行平台级权限允许的操作，不自动拥有实例内的数据权限。
  4. Given 用户没有某权限，When 通过接口直接调用，Then 服务端拒绝（不能只靠隐藏界面按钮）。
- 业务规则：
  - 权限是代码里的固定集合；角色是权限的组合；授权是 (用户, 角色, 实例[, 机构])。
  - 内置角色（AI 建议，待用户确认）：平台管理员、实例管理员、模板设计人、机构管理者、填报人、只读查看者。第二期增加审核人、批准人。
  - 机构级角色（填报人、机构管理者）必须绑定到某个机构；见 Q-005。
  - 授予、撤销、角色变更都写审计日志。
- 边界和异常：
  - 最后一位实例管理员被撤销：拒绝，必须保留至少一位。
  - 用户离开：停用账号（不是删除），授权保留为历史，不再生效。
- 相关：REQ-001、REQ-004、REQ-019、Q-005、Q-016；老系统：`UserRole.sql`、`NavMenuRole.sql`（反面教材：一个用户只有一个 `UserRoleId`，菜单权限与功能权限混在一起）

## REQ-004 用户管理与批量导入

- 优先级：MVP（1a）
- 状态：有效
- 来源：用户回答（需要用户管理）；代码推断（未确认：老系统有 Excel 批量导入用户，见 `UserImportHandler.cs`）
- 用户故事：作为实例管理员，我想要创建、停用用户并批量导入，以便快速开通几百个机构用户。
- 验收标准：
  1. Given 一份合法的用户 Excel，When 导入，Then 所有用户在同一事务内创建并带上指定的角色和机构，失败则一个都不创建。
  2. Given 文件有错误，When 导入，Then 返回逐行逐列的错误报告（行号、列名、原因），不写入任何数据。
  3. Given 邮箱已存在于本实例，When 导入，Then 该行报"重复"，不覆盖已有用户。
- 业务规则：
  - 邮箱在平台内唯一标识一个人；同一个人可属于多个实例。
  - 用户停用后保留身份，以便审计署名。
- 边界和异常：
  - 一次导入的最大行数：1 万行（AI 建议，待用户确认）；超过则要求拆分。
  - 导入过程中途失败：整体回滚。
- 相关：REQ-003、REQ-013、REQ-019；老系统：`UserInfoImport.razor`、`UserImportHandler.cs`

## REQ-005 机构管理

- 优先级：MVP（1a）
- 状态：有效

## REQ-008 计量单位

- 优先级：MVP（1a）
- 状态：有效
- 来源：用户回答（数值、文本、日期、枚举、计算类型）；代码推断（未确认：老系统 `UnitofMeasure` 带 `DataType`、`ValidationRule`）

## REQ-012 主数据的停用与删除规则

- 优先级：MVP（1a）
- 状态：有效
- 来源：用户回答（老系统几乎每个模块都用逻辑删除，用户认为没必要，要求评估并由 AI 建议）；AI 建议，用户默认（评估结论见下）
- 用户故事：作为实例管理员，我想要明确的"停用"与"删除"语义，以便既不丢历史，又不被无用数据拖累。
- 验收标准：
  1. Given 一条主数据（计量单位、属性、分类组、分类、选项、机构、分类取值、财年、报告期）没有被引用，When 删除，Then 物理删除并写审计日志。
  2. Given 它已被引用，When 删除，Then 拒绝并提示"停用"。
  3. Given 它被停用，When 设计新模板，Then 不可选；When 查看历史模板或填报，Then 仍正常显示。
  4. Given 角色授权、映射、设置、通知被撤销或移除，When 操作完成，Then 物理删除；"谁何时撤销"由审计日志记录。
- 业务规则：
  - **不使用通用的逻辑删除标志**（例如老系统每张表的 `Status` 1/0）。每个对象类型的生命周期是明确的：主数据"有效/已停用"；模板"草稿/已发布/已停用"；用户"启用/停用"。
  - 草稿模板可物理删除；已有填报的模板永不删除。
  - 填报数据与提交快照：用户不能删除；到期由留存任务处理（REQ-033）。
  - 审计日志只追加。
  - 唯一约束只约束"未被物理删除"的行，不需要带条件的索引。
- 边界和异常：
  - 停用有层级的节点：其子节点保持有效但在新模板中以"父已停用"提示（AI 建议，待用户确认）。
- 相关：REQ-016、REQ-019、REQ-033

## REQ-013 科目表批量导入与跨实例复制

- 优先级：MVP（1a）
- 状态：有效
- 来源：代码推断（未确认：老系统 COA Import，设计稿 `COA_Import_Redesign.md` 记录了其问题）；AI 建议，待用户确认（复制）
- 用户故事：作为实例管理员，我想要用一份 Excel 一次性导入计量单位、属性、分类组和分类，并能从别的实例复制科目表，以便快速建立新项目。
- 验收标准：
  1. Given 一份含四个工作表的 Excel，When 点击提交，Then 四类数据在**同一个事务**中写入，任一行失败则全部不写。
  2. Given 属性引用的计量单位在同一个文件的另一个工作表里，When 校验，Then 外键按"数据库中已有 ∪ 本文件即将写入"解析，通过。
  3. Given 校验失败，When 查看结果，Then 每个错误精确到"工作表、Excel 行号、列、原因"，并可在页面内就地修正后再提交。
  4. Given 同一业务键在文件内重复，When 校验，Then 报重复（标出两处行号）。
  5. Given 我是实例 B 的管理员且有权读取实例 A 的科目表，When 选择"复制自实例 A"，Then 复制一份独立副本，之后两边互不影响。
- 业务规则：校验分五级：类型格式、字段规则、文件内重复、数据库键冲突（每个工作表批量查一次）、跨表外键。
- 边界和异常：
  - 大文件：超过 1 万行提示拆分。
  - 重复提交：同一文件重复提交不产生重复数据（幂等，按业务键）。
  - 导入时有人同时改科目表：提交时重新校验，冲突则整体失败。
- 相关：REQ-008 到 REQ-012、REQ-019；老系统：`COA_Import_Redesign.md`（其 P1 到 P7 七个问题都是本需求要避免的）、`BulkImport/ImportOrchestrator.cs`

## REQ-014 Excel 加载项（模板设计工具）

- 优先级：MVP（1a）
- 状态：有效
- 来源：用户回答（模板设计保留 Excel + 加载项；加载项登录平台、通过 API 实时拉取 COA）；代码推断（未确认：老系统 `GDCT_TDT` 的功能）
- 用户故事：作为模板设计人，我想要在 Excel 里直接选择属性和分类并插入模板，以便制作模板又快又不出错。
- 验收标准：
  1. Given 设计人已在加载项中登录并选择了实例，When 打开属性选择，Then 看到该实例当前有效的属性（实时来自平台），选择后插入到指定列头。
  2. Given 选择分类组和分类，When 指定行号，Then 插入到该行，并在工作表里记录它与 COA 编码的映射。
  3. Given 选择"初始化工作表"，When 执行，Then 生成符合平台约定的工作表表头和结构。

- 业务规则：
  - 加载项通过平台 API 访问数据，不再依赖"工作簿里先放好 Attribute 工作表"。

- 边界和异常：
  - 令牌过期：提示重新登录，不丢工作簿内容。
  - COA 项被停用：插入时提示并拒绝。

## REQ-027 提交、撤回、重新提交与截止

- 优先级：MVP（1b）
- 状态：有效
- 来源：用户回答（截止日前机构可撤回修改后重新提交）；AI 建议，待用户确认（截止后锁定，由管理员延期或重新打开）
- 用户故事：作为填报人，我想要提交填报、并在截止前能撤回更正，以便数据既正式又可修正。
- 验收标准：
  1. Given 所有必填单元格已填且校验全部通过，When 提交，Then 状态变为"已提交"，保存一份不可变的**提交快照**，数据变为只读，并向机构管理者发送确认通知。
  2. Given 有校验错误或缺必填，When 提交，Then 拒绝并列出每个问题的位置。
  3. Given 已提交且未到截止，When 撤回，Then 状态回到"填写中"，可修改；再次提交产生新的快照，旧快照保留。
  4. Given 已过截止，When 填报人尝试撤回或修改，Then 拒绝。
  5. Given 已过截止，When 实例管理员对某机构"延期"（新截止日）或"重新打开"，Then 该机构的填报可再修改，并写审计（谁、原因、新截止日）。
- 业务规则：
  - 提交快照包含所有单元格值、公式结果、模板版本、提交人、时间；是第二期审批和报表的依据。
  - 截止时间的时区和精度见 Q-015；系统按服务端时间判定，不信任客户端时间。
  - 提交和撤回都需要拿到所有工作表的锁，或确认无人持锁。

## REQ-031 安全与隐私

- 优先级：MVP（贯穿）

- 用户故事：作为平台管理员，我想要系统在设计上就满足安全和隐私要求，以便顺利通过评估。
